# 분석 화면 재검토와 리팩토링 방향

2026-11-19 · 검토 기준 main `0f08908d`(#735), 구현 기준 `98dfce0b`(#736)

#736에서 기본 보기를 변화 시기 막대와 선택 신호 하나로 줄이고 성능이 부족한 전망을 제한했다. 이번에는 그 변경 위에서 고정 좌우 배치, 기본 표시와 조작 구조를 바꾼다. 아래 진단은 #735 검토에서 출발했고 구현 내용은 마지막 절에 정리했다. LLM 서버 연결과 실제 답변 유용성은 별도로 확인한다.

## 판단

현재는 화면의 역할과 기본 노출 규칙을 바꾸는 프런트엔드 리팩토링이 필요하다. 문장을 더 짧게 만들거나 그래프를 더 작은 칸에 넣는 방식으로는 해결하기 어렵다.

이전 개편은 선택한 분석을 이어 보는 연결을 개선했다. 그러나 연결된 정보를 계속 화면에 남기는 정책까지 함께 적용했다. 사용자는 선택한 조사보다 더 많은 신호·모델·기간·조작을 동시에 해석하게 됐다. 이전에 타입 검사, 오류 없는 캡처와 선택 유지 확인을 주된 완료 근거로 삼은 평가는 사용자 이해와 시각적 집중을 충분히 평가하지 못했다.

공통 시간축은 유지할 가치가 있다. 기본 화면에 표시할 대상, 세부 분석에서 필요한 맥락, 기록 입력을 언제 열 것인지의 결정이 부족하다. 이 결정이 현재 사용자에게 넘어가 있다.

## 확인한 범위

- 원격 조회 후 로컬 HEAD와 `origin/main`이 같은 `0f08908d`임을 확인했다. #734 이후 #735 한 건이 병합됐다. #735의 PR head `93184c8c` CI는 성공이었다. 병합 커밋의 PR-triggered 검사 조회는 결과가 없어 이 둘을 구분한다.
- 검토 중 `.other/img`가 12장에서 현재 6장으로 갱신됐다. 최초 목록에서 모니터링 2장·모델 반응·주파수의 원본 캡처 4장을 직접 열었고, 갱신된 현재 6장도 모두 직접 열어 보았다. 현재 파일은 `01_화면구성`, `02_베어링_변화순서`, `03_베어링_전망`, `04_공기압축기_3상전압과운전상태`, `05_공기압축기_모델학습범위`, `06_판단기록`이다. 이미지와 README는 변경하지 않았다.
- 화면 소유 관계, 기간·신호 선택, 시간축 렌더링, 전망 표시, 판단 입력을 소스에서 대조했다. 이번에는 앱을 새로 띄우거나 브라우저 조작·계산·LLM 응답 품질을 독립 재검증하지 않았다. 이미지의 주석·예시 판단도 실제 제품의 자동 해석으로 취급하지 않았다.
- 외부 제품은 공식 문서와 공개 자료를 조사했다. TrendMiner의 공식 화면 이미지는 직접 열어 보았다. Seeq·Augury의 일부 이미지 원본은 HTTP 403으로 열리지 않아 해당 화면을 직접 시각 검증했다고 주장하지 않는다. 유료 제품에 로그인한 사용성 검증도 수행하지 않았다.

| --- | --- | --- |
| 관측 화면에 신호 3개·모델 2개·전망 기준·판단 입력이 공존 | 파악, 비교, 전망, 기록 중 지금 해야 할 작업이 선명하지 않음 | 관측은 대표 변화와 관련 맥락을 우선하고, 조사·입력은 선택한 작업으로 열기 |
| 모든 분석의 왼쪽에 같은 시간축을 상시 유지 | 주파수·분포·모델 분석에서도 관련 없는 곡선이 주 분석과 시선을 나눔 | 분석별로 필요한 맥락만 작은 영역에 표시하고, 본문 폭을 분석에 배정 |

| 한 줄 커서 정보가 모든 신호·모델 값을 나열 | 같은 시점을 읽으려는 짧은 동작이 여러 숫자를 다시 해독하는 작업이 됨 | 선택한 신호 값은 해당 곡선 옆에, 비교 대상을 추가했을 때만 함께 표시 |
| 버튼·제목·입력 양식의 시각적 무게가 비슷함 | 빈 판단 폼도 실제 발견과 비슷한 면적을 차지하고, 조사 진입점과 보조 조작이 경쟁 | 결과·선택·설정·입력을 크기와 위치로 구분. 판단은 한 진입점에서 필요할 때 열기 |
| 마지막 측정, 묶인 변화 시기, 개별 변화, 초기 기준, 미래 범위를 함께 표시 | 같은 숫자 옆에 서로 다른 시간 범위와 분모가 등장 | 각 분석의 대상/기준을 한 번 명시하고 결과 가까이 유지 |

예를 들어 베어링의 묶인 변화는 69–123회지만 RMS 변화는 72–123회다. 모델의 48/55회와 RMS 기간 비교의 52회는 다른 범위에서 나온 수다. 계산이 맞아도 범위를 계속 기억하며 읽게 하면 직관적인 화면이 되기 어렵다.

### 코드가 이 구성을 계속 만들게 되는 지점

- `AssetWorkspace.svelte:191`은 분석 중에도 `AssetSummary`를 유지하고, `:294`는 모든 분석에 동일한 좌우 비율을 적용한다.
- `AssetSummary.svelte:477`은 전체 `lanes`, 운전 상태, 모델 목록을 같은 `AssetTimeline`에 전달한다. `AssetTimeline.svelte:60`의 `compact`는 주로 높이를 줄이며 `:180`의 반복 표시 대상을 줄이지 않는다.
- `AssetSummary.svelte:521`은 판단 패널을 `inline`으로 열고, 바로 아래에는 전체 분석 동작을 붙인다. 관측 화면이 입력 화면 역할까지 맡는다.
- `AssetTimeline.svelte:130`의 공통 값 줄, `:180`의 모든 신호, `:249`의 운전 상태, 모델 반복 출력이 함께 쌓인다. 이 컴포넌트가 관측·비교·전망의 표시 정책까지 소유한다.
- `ModelRunEvidence.svelte:405` 이후는 모델 선택·측정 선택·원본 확인·메타데이터·후속 이동·비교 측정·AI·특징 비교를 이어서 배치한다. 왼쪽 요약이 추가돼도 본문 자체의 행동 계층은 그대로다.

파일의 줄 수 자체가 결함이라는 뜻은 아니다. 데이터 읽기, 선택, 표시 여부, 기록 입력의 책임이 묶여 있어 기능이 생길 때마다 기본 화면에 추가되기 쉬운 것이 문제다.

## 2. 먼저 보완할 해석·조작 문제

**전망 수치의 강조 — 높은 우선순위.** 현재 캡처 03은 단순 예측보다 부정확해 예측선을 숨기면서도 ‘가장 이르면 추가 60회 뒤’와 빨간 수직선을 표시한다. `AssetSummary.svelte:331`의 `trusted`와 `:333`의 `reach`가 별개로 전달되고, `AssetTimeline.svelte:197`과 `:237`의 도달 수치·선은 `trusted`를 조건으로 삼지 않는다. 경고를 함께 썼다는 사실만으로 수치의 시각적 확신이 사라지지는 않는다. 관측 요약에서는 활용하기 어려운 예측임을 결과로 보여 주고, 불확실한 도달 수치를 운영상 기한처럼 강조하지 않아야 한다.

‘초기의 2·5·10배’는 프로그램이 만든 비교선이다(`AssetSummary.svelte:332`). 현장 관리 기준이나 검증된 고장 한계와 구분해야 한다. 잔여 수명은 제거할 기능이 아니라, 사용자가 명시한 종료 기준·계산 가능 조건·예측 성능에 맞춰 전용 전망 화면에서 다룰 항목이다. 초기의 10배 도달 전망을 고장 잔여 수명으로 부를 수는 없다.

**시간축 선택의 접근성 — 보완 필요.** `AssetTimeline.svelte:177`은 키보드 관련 경고를 억제하고 포인터/클릭으로 시점을 고른다. 신호 이름 버튼은 초점을 바꾸지만 시점 이동을 대체하지 못한다. 이전/다음 측정과 키보드 조작을 공통 선택 모델에 연결해야 한다. 이는 이번에 브라우저에서 재현한 결과가 아니라 현재 코드상 확인한 경로다.

**선택 소유 관계 — 리팩토링에 포함.** `AssetTimeline.svelte:110`은 진동 선택은 상위로 보내지만 시각 기반 선택은 로컬 `pinned`에 둔다. 전력 시점 조사도 후속 분석과 이어지게 하려면 hover와 확정 선택, 측정 번호와 시간 구간을 구별하는 공통 계약이 필요하다. 새 서버 기록 체계는 필요하지 않다.

이 사례에서 도출한 적용 판단은 **선택한 작업에 맞춰 화면을 재구성하고, 사용자에게 필요한 맥락만 남기는 것**이다. 화려한 차트, 어두운 테마, 카드 수 증가, AI 패널 상시 노출을 최근 방향으로 권고하지 않는다.

| 3상 전력 | 같은 시간축의 관련 상 값/불평형, 선택 시점 비교 | 네 지표를 모두 같은 크기로, 현재 조사와 무관한 표/조작 선행 |
| 전망·예상 여유 | 예측 활용 가능 여부, 실측/미래 구분, 현장 기준과 조건부 도달 결과 | 근거 없는 위험 기한처럼 보이는 숫자, 관측 화면의 임의 배수 선택 |
| AI·판단 | 선택한 조사에 연결된 한 진입점, 질문·필요한 답변·메모 | 초기 화면부터 기록 양식 노출, 화면마다 중복 채팅. 전력 AI 확장도 자료·업무 유용성부터 평가 |

관측의 문구는 ‘수직 RMS가 72회부터 높아지고 마지막 측정에서 5.78 g’처럼 관찰된 결과를 짧게 전달할 수 있다. 이 문장을 사용자 가치에 관한 질문 제목으로 바꿀 필요는 없다. 개별 사용자가 다른 순서로 조사할 수 있어야 하며, 고정된 마법사 흐름을 강요하지 않는다.

## 5. 구현 경계와 작업 순서

1. **화면별 기본 표시를 먼저 확정한다.** 1440×900·1280×900에서 관측/모델/주파수의 기본 상태와 선택 후 상태를 실제 데이터로 구성한다. 주 그래프·핵심 결과·주 조작이 첫 화면에서 함께 보이게 한다. 모든 기능을 위로 당기거나 글자를 줄여 맞추지 않는다.
2. **`AssetWorkspace`의 고정 배치를 바꾼다.** 상세 분석은 본문을 넓게 쓰고 현재 신호·기준·선택 측정은 짧은 맥락 영역으로 유지한다. 전체 시간축은 필요할 때 열 수 있다. 모델 화면의 점수 곡선은 해당 본문이 소유하게 해 좌측 요약을 없애도 기능을 잃지 않게 한다.
3. **표시와 선택·읽기·입력을 나눈다.** 기존 `record-context.ts`, 주소 전달, 판단 초안/저장 기능을 재사용한다. `AssetSummary`의 데이터 준비를 표시 정책에서 분리하고, `AssetTimeline`은 선택된 신호와 축을 그리는 역할로 좁힌다. hover는 일시 값, 확정 선택은 후속 분석 대상이다. 전망 계산·기준 조작은 전망 화면, 판단 입력은 요청 시 열리는 기존 패널이 맡는다.
4. **화면별 조작을 통합한다.** 기간 비교는 기간 선택, 주파수는 대역/측정 선택, 모델은 모델/측정 선택을 각 그래프 가까이에 한 번 배치한다. 같은 축·단위·A/B 범례·선택 강조의 규칙을 맞춘다. 선택 강조와 위험 경고에 같은 빨간색을 쓰지 않는다.
5. **실제 조사로 마무리한다.** 베어링 변화 선택 → 실제 진동 추이·파형과 주파수 변화 확인 → 필요 시 모델 점수 또는 AI 질문 → 판단·재방문, 공기압축기 전압 변화 → 같은 운전 수준 비교 → 모델 학습 조건 확인을 수행한다. 상태 유지와 입력 보존 외에 사용자가 발견·비교 결과를 읽는 과정도 확인한다.

현재 Svelte와 기존 SVG/Canvas, 계산 API를 기반으로 이 경계를 바꿀 수 있다. 이번 확인에서 차트 엔진의 성능 부족이 원인이라고 입증되지 않았으므로 라이브러리 교체부터 권고하지 않는다. 필요할 경우 실제 병목이 드러난 그래프만 축·커서·범례·데이터 생략 방식을 비교한다. 프런트엔드의 역할 분리와 화면 구성 교체가 이번 리팩토링의 중심이다.

완료 기준은 오류 없는 페이지와 캡처 수가 아니다. 기본 화면에서 중요한 현상과 비교 기준을 찾을 수 있고, 선택한 측정에서 필요한 분석을 수행하며, 분석 후 무엇이 달라졌는지 사용자가 설명할 수 있어야 한다. 데이터가 없거나 모델이 도움이 되지 않는 경우에도 명확한 결과를 제공해야 한다. 이를 확인하는 짧은 실제 작업 평가를 수행하며 이번 문서만으로 사용성 개선이 검증됐다고 취급하지 않는다.

## 6. 구현

고정된 관측/상세 좌우 배치를 제거했다. 상세 분석이 전체 폭을 사용하고 모델 화면은 점수 그래프를 직접 소유한다. 관측은 선택한 신호 하나의 초기·변화·마지막 값과 그래프를 우선하며, 다른 신호와 운전 조건은 명시적으로 함께 본다. 모델 점수는 별도 이상 징후 화면에서 선택한 모델 하나를 조사하며, 모델 간 비교는 사용자가 요청할 때만 연다. 조사 동작은 그래프 앞에서 선택한다.

모니터링의 자동 전망·배수 기준과 중복 요약 조회, 이전 표시 모드, 사용하지 않는 그래프 컴포넌트를 제거했다. 전망 기능과 조건부 예상 여유는 해당 분석 화면에 유지한다. 이름은 등록된 표시 이름을 보존하고 공개 베어링 식별자를 읽기 쉽게 표시한다.

원본 운영 작업공간을 복사한 격리 스택에서 베어링·공기압축기를 조사한다. 실제 캡처와 LLM 답변 확인 결과는 PR에 구분해 기록한다. 사용자 운영 스택과 LLM 서버, 기존 `.other` 자료는 보존한다.

### 실제 화면 확인 (2026-11-20)

- 원본의 복사본에서 베어링과 공기압축기를 조작했다. 1440×900·1280×900에서 주 그래프와 비교값을 확인하고 390 px에서는 가로 넘침을 확인했다.
- 다른 변화 선택 → 기간 비교 → 주파수 → 모델 → 복귀 → 새로고침에서 선택을 유지했다. 모델의 과거 측정으로 Home 이동, 실측 키보드 선택, 판단 초안 보존과 저장 후 재방문도 확인했다.
- 실제 LLM에 두 설비의 질문을 보냈다. 베어링은 모델 답변과 계산 요약 대체가 모두 발생했다. 공기압축기는 이전 측정과 전류·전력 변화를 설명했지만 질문한 학습 범위 해석은 충분하지 않았다. 답변 품질을 전반적으로 해결했다고 취급하지 않는다.
- 베어링의 답변 생성 후에도 화면이 작성 중에 남는 문제를 재현했다. 질문 전송과 조회의 취소 처리를 분리한 뒤 답변 표시와 판단 메모 전환을 확인했다.

### 분석별 작업 배치

비교 화면은 대상·기간·조건 변경을 같은 헤더에 둔다. 공통 설정 컴포넌트에서 결과 그리드의 행 배치를 제거했다. 진동 관계는 두 산점도와 선택한 측정의 실제 값을 나란히 두고, 선택한 회차를 모델·파형에 전달한다. 전망은 그래프와 현장 기준·적용 결과를 나란히 두며 입력 초안과 계산한 기준을 구분한다. 3상 전력은 우선 확인할 시점 주변을 기본으로 조사하고 전체 기간을 전환한다. 선택 시점의 세 상을 막대로 비교하고 기준 범위와 자세한 수치를 구분한다.

추가 확인: 관계 점 선택→모델→원본 파형, 두 종류 전망의 기준 초안·적용, 화면 이동 후 판단·AI 질문 초안 보존, 3상 주변/전체 기간과 고정된 그래프 범위 안의 키보드 선택을 실제 복사 데이터에서 확인했다. 브라우저에서 기록한 JavaScript·HTTP 오류는 없었다. 타입 검사·빌드를 통과했다. 자동 검사 통과로 사용자 이해도가 입증됐다고 보지는 않는다.

두 브라우저를 동시에 조작한 추가 검사에서는 공기압축기 전망의 `forecast_store_unavailable` 503 응답 한 건을 확인했다. 같은 요청의 단독 재조회는 200이었다. 발생 원인을 이번 프런트엔드 변경으로 확정하지 않으며, 화면에는 재시도 동작이 표시됐다. 오류가 전혀 없는 시스템으로 평가하지 않는다.
